# Adaptive Fast Execution 实施与评测计划

## 目标

实现并量化验证 `adaptive-fast-execution` Skill，使低风险短任务减少设计确认、文档与无关验证，同时确保复杂、长时和高风险任务不会错误降级。

## 受控表面

- 锁定：风险清单、升级条件、评测断言和评分规则。
- 可编辑：两个 Skill 的说明、触发描述和快速执行协议。
- 只追加：每轮运行结果、计时、token、评分与分析记录。
- 人工控制：安装覆盖个人 Skill、GitHub 仓库可见性及社交媒体公开发布。

## 实施步骤

1. 在仓库内创建 `skills/adaptive-fast-execution/`。
2. 复制并最小修改 `brainstorming` Skill，使其只对复杂、长时或高风险创意工作使用硬设计门。
3. 建立低风险、范围升级、长任务和高风险测试用例。
4. 固定断言后再运行测试，避免根据输出修改评分标准。
5. 对每个用例分别运行有 Skill 与无 Skill 基线，记录耗时与 token。
6. 聚合正确率、流程开销和安全降级结果，生成静态查看器和 Markdown 报告。
7. 只根据失败轨迹修改 Skill，保留原始结果；复测关键用例。
8. 显式提交范围内文件，推送到 GitHub 并创建草稿 PR。
9. 根据最终数据生成中英文 X 文案和一张项目发布配图，保存为待审素材，不直接公开发布。

## 最小成功标准

- 所有低风险任务直接进入实施，无多轮设计确认，并保留相关验证。
- 所有长任务、复杂任务和高风险任务均未错误进入快速模式。
- 范围扩大的任务能够明确退出快速模式。
- 快速模式相对基线在时间、token或确认步骤中至少一项有明显下降。
- 报告披露样本量、测试环境和局限，不把小样本结果夸大为普遍结论。

## 发布边界

GitHub 发布包含 Skill 源码、测试用例、可复查的结果和报告。当前仓库没有远端，因此在本地验证完成后再确定新 GitHub 仓库的名称与公开/私有属性。X 等媒体只准备草稿与图片；实际发帖需要用户最终确认。
